QuantLab Documentation

QuantLab backtests trading strategies written in Python against daily price history. Everything runs in your browser. Python runs through Pyodide, and your data and code never leave the machine.

Quick Start

  1. On the Data tab, 23 instruments (10 years of daily Nasdaq data) are already loaded. Drop more CSV files there to add your own.
  2. On Backtest, pick an instrument and a benchmark, and choose a strategy from Start from.
  3. Edit the code and press Ctrl+Enter (⌘+Enter on a Mac) or Run backtest.
  4. Read the headline numbers, then check the drawdown chart and the trades table to understand why the result looks the way it does.
  5. Use Research tools to see whether the result survives different parameters, a different period, and reshuffled returns.

A strategy is a Python function that runs once per trading day and returns how much of your account to have invested:

PARAMS = {"n": 200}

def on_bar(ctx):
    avg = ctx.sma(PARAMS["n"])      # 200-day simple moving average
    if isnan(avg):                  # not enough history yet
        return 0.0
    return 1.0 if ctx.price > avg else 0.0   # 100% invested or 100% cash

Editor shortcuts: Tab and Shift+Tab indent, Ctrl+/ toggles comments, Ctrl+S saves the strategy in this browser. Press Esc then Tab to move focus out of the editor. Your current draft is kept automatically.

Getting Data

QuantLab reads the CSV export from Nasdaq.com’s historical quotes page. Columns are Date, Close/Last, Volume, Open, High, Low, newest row first, and prices may start with $. Yahoo Finance exports (Date, Open, High, Low, Close, Adj Close, Volume) also work. The raw close is always the trading price; an Adj Close column is used only to work out the dividends (see below). The browser and the Python engine read files with exactly the same rules.

  1. Open https://www.nasdaq.com/market-activity/etf/spy/historical. Stocks use /stocks/aapl/historical instead.
  2. Choose 10Y, the longest range offered, and download.
  3. Drop the file on the Data tab. Nasdaq names every file HistoricalData_<number>.csv, so you’ll be asked for the ticker. Renaming the file to SPY.csv first skips the question.

Uploaded files are stored in your browser (IndexedDB) and reappear the next time you open QuantLab in the same browser. To bundle files with the site for everyone, put them in data/ and list them in data/manifest.json.

The suggested starting set covers the main asset classes: SPY QQQ IWM DIA (US stocks), TLT IEF SHY (Treasuries), GLD SLV USO (commodities), EFA EEM (international), XLK XLF XLE XLV (sectors), and AAPL MSFT NVDA AMZN JPM XOM KO (single stocks).

Dividends & Total Return

Nasdaq's Close/Last is adjusted for splits but not for dividends, so on its own it understates the return of SPY by about 1.3% a year and of bond ETFs by 3–4%. QuantLab trades on the real price and pays dividends into the account on each ex-date, so P&L is total return while your signals see the prices a trader would have seen. On an ex-date, before that day's orders fill, the account receives shares held at the previous close × the dividend; a position bought at the ex-date open doesn't get it, and a short pays it. An ex-date that falls on a weekend or holiday counts on the next trading day. The benchmark and Instrument Analytics use total-return series (dividends reinvested). The Dividends received statistic shows the cash paid in, and ctx.dividend is the dividend per share going ex today (0 on most days). Dividends come from:

  • an Adj Close column (Yahoo Finance): the dividend on each ex-date is recovered from the step in the adjustment factor, D = close[t-1] × (1 − F[t-1] / F[t]) with F = adj / close;
  • a dividend history file dropped on the Data tab. Any file with an ex-date column (ex_date, ex-date, Ex/EFF Date, Ex-Dividend Date or Date), an amount column (amount, Cash Amount, Dividend or Dividends) and no close column is read as dividends, not prices. That covers a plain ex_date,amount file, Nasdaq's Dividend History export ($ amounts, MM/DD/YYYY dates; rows whose Type isn't Cash are skipped) and Yahoo's Date,Dividends.

The ticker comes from the file name with suffixes such as _dividends, -dividends,  dividends or _divs removed, so KRSB_dividends.csv is KRSB's. If the name has no ticker, a form asks which one it is. Dividends are stored per ticker in this browser, apart from the prices, so they can arrive first: they're kept (listed under the instruments table) and attached when that ticker's prices are added. The Dividends column of the instruments table shows how many payments fall inside each price history; Remove Dividends asks for a second click and can be undone.

A split history (Date,Stock Splits with values like 4:1) is applied only if the prices jump by about the ratio at the split, i.e. they are unadjusted; already-adjusted prices are left alone. Each run's subtitle says whether dividends were included or the run is price-only, and names instruments with no dividend data (Dividends missing). The bundled files are Nasdaq downloads and carry no dividends. Include dividends under Account & Execution (on by default) turns all of this off for price-only results.

Other File Layouts & Parquet

Besides Nasdaq and Yahoo CSVs, the Data tab reads price tables with any delimiter (comma, semicolon, tab or |), decimal commas (1.234,56), European dates (31.12.2024) and other column names (Datetime, Last Price, Settle, o/h/l/c/v …), in .csv, .tsv or .txt files. When it can't tell which column is which, it asks you to map the Date, Time, Open, High, Low, Close and Volume columns. Parquet files are read with pandas and fastparquet, which download from the Pyodide CDN the first time (about 20 MB). In Python, engine.load_table("prices.parquet") or engine.load_table("prices.txt", mapping={"date": "Fecha", "close": "Cierre"}) does the same.

Calendars, Crypto & Intraday Bars

Statistics are annualized with each instrument's bars per year: trading days a year × bars per day. Daily data that trades on weekends (crypto) uses 365 days; other daily data uses the usual 252. The Calendar column on the Data tab shows what was detected and lets you choose: NYSE (252), Weekdays (260, e.g. FX) or Every day (365). A portfolio uses the busiest calendar among its instruments. Each run records the calendars it used.

Intraday bars load from files whose dates carry a time: 2024-01-02 09:30, 2024-01-02T09:30:00Z, 01/02/2024 1:05 PM, separate Date and Time columns, or Unix seconds or milliseconds (as TradingView exports). Times are taken as written (a time-zone suffix is ignored); a midnight time counts as a daily bar. With intraday bars, indicator lengths count bars, ctx.time is the bar's time ("09:30"; None for daily data), annualization multiplies by the median bars per day (78 for 5-minute US equity bars), interest on cash accrues once per calendar day, dividends are paid on the first bar of their ex-date, the From/To dates include the whole day, and a daily benchmark only moves once its day has closed.

Futures

Set an instrument's Type to Future on the Data tab and positions in it take no cash: the cash stays in the account as collateral and earns interest, so a futures position's return is its price change plus interest, as with a real margin account. Shorting a future pays no borrow fee, and leverage through futures borrows no cash; the notional still counts toward gross exposure, Max Leverage and margin calls. Sizes are in units of the price (index points, barrels …), so leave Fractional shares on, or use a multiplier-adjusted price series for whole contracts.

Continuous Futures on the Data tab stitches single-contract files into one series. It rolls either a set number of bars before each contract's last bar (on a day both trade) or on the first day the next contract trades more volume, and back-adjusts the history at each roll: ratio multiplies earlier prices by new ÷ old (returns stay exact and prices positive), difference adds the gap (point changes stay exact; long histories can go below zero, and those bars are dropped), none splices raw prices so the roll gaps show up as returns. The roll happens at the roll day's close: that day's return is the old contract's. In Python: engine.continuous_futures([esh, esm, esu], "ES", roll="days", days_before=5, adjust="ratio"); its .rolls lists every roll and gap.

Other Currencies

Set an instrument's Currency on the Data tab when its prices aren't in the account's Base Currency (Account & Execution; USD by default). Runs then convert its prices and dividends with a loaded FX price series: EURUSD (dollars per euro) multiplies, USDEUR divides, and Yahoo names such as EURUSD=X work too. Each bar uses the FX close of the same day (the previous day's for intraday bars with daily FX data); bars before the FX history starts are left out. The conversion is unhedged, so returns include the currency's moves, and the run notes say which series was used. Volume stays in shares and fundamentals in their own currency. In Python: set ds.currency = "EUR" and call engine.in_base(ds, "USD"), or engine.to_base_currency(ds, fx).

Point-in-Time Fundamentals

Drop a CSV of fundamentals on the Data tab: a date each value became known (a column named Filing Date, Filed, Available, Report Date, Announcement Date or Acceptance Date), optionally Period End, one column per field (EPS, Revenue, Book Value …; text columns are ignored) and, for several instruments in one file, a Ticker or Symbol column. Without one, the ticker comes from the file name (AAPL_fundamentals.csv) or you pick it. Field names become lower case with _: Book Value → book_value.

def on_bar(ctx):
    eps = ctx.fundamental("eps")          # NaN until the first filing is known
    return 1.0 if ctx.price / eps < 15 else 0.0

def signals(data):                       # one value per bar, point in time
    eps = data.fundamental("eps")        # portfolios: data["AAPL"].fundamental("eps")
    ...

A value counts from the first bar after the day it became known, because filings often come out after the close; the strategy can trade on it at the next bar's open at the earliest. A row with only a period end is assumed known 45 days later, with a warning: using period-end dates is one of the most common sources of look-ahead in fundamental backtests. Restated values are fine as separate rows with their own dates. ctx.fundamentals gives every loaded field at once.

Delistings & Survivorship

When an instrument's data ends before the backtest does (delisted, acquired, or a file that is simply out of date), its position is closed on the next bar at its last close, with no costs, and it can't be traded again; the run notes say so. engine.Config(delisting_return=-0.3) books a loss on that last price instead, as studies of delisted stocks suggest for failures. A portfolio of three or more instruments that all trade to the end of a test of three years or more gets a survivorship bias note: a universe picked today leaves out the names that disappeared. The cure is data that includes them.

Data Quality

Every instrument is checked when it loads, and the Data tab lists what was found. Nothing is dropped silently: rows without a valid date and positive close are skipped and counted, impossible highs/lows are widened and counted, and duplicates keep the later row. The checks against the exchange calendar (NYSE holidays and special closures; every day for crypto that trades on weekends) report missing sessions and bars on closed days. Runs of identical closes are flagged as stale, and one-day moves above 12% that are also 8 standard deviations from the last 60 days are flagged as possible unadjusted splits or bad prints.

Writing a Strategy

Your code is ordinary Python 3.12. It must define on_bar(ctx), or signals(data) for the vectorized style. A few names are available without importing them: math, statistics, random, datetime, qt (indicator functions), walk_forward (see Machine Learning), isnan and NAN. The rest of the standard library can be imported normally, and so can NumPy, pandas, SciPy and scikit-learn.

For longer code, open the Editor tab (or Open Full Editor on the Strategy panel). It gives the same editor the full height of the window, with a text-size switch, and keeps the Run button, errors, headline numbers and equity curve beside it. Your code is shared between both views.

What on_bar Returns

ReturnMeaning
1.0Hold the asset with 100% of equity.
0.5Hold 50% of equity in the asset and the rest in cash.
0.0Sell everything and hold cash.
-1.0Short 100% of equity. Requires Allow shorting; otherwise it is treated as 0.
2.0200% long with borrowed money. Requires Max leverage of 2 or more; the value is capped at that limit.

A weight is a target, so returning 1.0 every day trades only once. Small drifts are ignored by the rebalance band (2% of equity by default), so returning 0.5 every day doesn’t trigger a tiny trade each day.

Share Orders

To think in shares instead, call these and return nothing:

ctx.order(10)               # buy 10 shares (negative sells)
ctx.order_target_shares(0)  # end up with exactly 0 shares

Orders that need more cash than you have are reduced to what you can afford. Sells beyond your position are reduced too, unless shorting is on. Each reduction is counted in the Orders reduced statistic. If on_bar returns a weight, that weight wins over any market orders from the same bar.

Limit, Stop & Bracket Orders

Both order functions take options. Market orders fill at the next bar's open (or close); orders with a price rest and fill inside a later bar when its range reaches them.

ctx.order(10, limit=99.5)                    # buy at 99.5 or better
ctx.order(10, stop=105)                      # buy once the price rises to 105
ctx.order(10, stop=105, limit=106)           # stop-limit: triggered at 105, no higher than 106
ctx.order(10, at="close")                    # market on the next close (at="open": on the open)
oid = ctx.order(-5, limit=110, tif="gtc")    # good till cancelled; ctx.cancel(oid), ctx.cancel_all()
ctx.order_target_shares(0, stop=95, tif="gtc", oco="exit")    # a bracket: whichever fills first
ctx.order_target_shares(0, limit=110, tif="gtc", oco="exit")  # cancels the other
  • Fill price. A buy limit fills when the bar's low reaches the limit, at the limit, or at the open if the bar opens below it. A stop triggers when the high (low, for sells) reaches it and fills at the stop, or at the open after a gap. A stop-limit that triggers above its limit fills only if the price comes back to the limit.
  • Which order first. The bar is treated as a path from the open to the nearer extreme, the other extreme, then the close; orders fill in the order the path reaches them. With Pessimistic fills, a long position's path visits the low first and a short's the high first, so a bar that touches both a stop and a target hits the stop; a limit must trade through its price, not just touch it, and a stop-limit that gaps past its limit waits for a later bar.
  • Lifetime. tif="day" (the default) lives for the next bar only; "gtc" until it fills or is cancelled. ctx.open_orders lists resting orders. Target orders are sized when they fill, so an exit never turns into a new position, and one with nothing left to exit is dropped.
  • Costs. Market orders and triggered stops pay slippage, half the spread and impact. Limit fills provide liquidity and pay commission only.

Parameters, Memory & Setup

PARAMS = {"fast": 20, "slow": 100}   # numbers here can be swept in Research tools

def init(ctx):                      # optional: runs once before the first bar
    ctx.state["peak"] = 0.0

def on_bar(ctx):
    ctx.state["peak"] = max(ctx.state["peak"], ctx.price)   # ctx.state persists between bars
    if ctx.price < 0.9 * ctx.state["peak"]:
        return 0.0
    return 1.0 if ctx.sma(PARAMS["fast"]) > ctx.sma(PARAMS["slow"]) else 0.0

print() and ctx.log(...) output appears in the Output panel under the results. ctx.log prefixes each line with the bar's date. If your code raises an error, the message, the line number and the bar's date are shown, and the line is marked in the editor. The Output panel shows the first and last 20,000 characters of long output; Download Full Output saves all of it (up to 5 MB).

Modules: Code Shared Between Strategies

A module is a Python file in your browser's module library that any strategy can import. Click Modules above the editor, enter a name such as my_signals and press Create; the module opens in its own tab. Then, in a strategy:

from my_signals import trend        # or: import my_signals

def on_bar(ctx):
    return trend(ctx, 50)

Modules get the same helpers as strategies (qt, isnan, math …) and may import each other and any package. Every run imports them afresh, so a module-level variable never carries over from one run to the next. Runs use the text in the editor, saved or not; Ctrl/⌘+S saves the visible module to the library, and an orange dot marks a tab with unsaved changes. A module can't take the name of a Python or QuantLab module (math, numpy, engine …). Errors inside a module open it at the failing line. Each run records a SHA-256 of every module it imported; Re-run in the History tab uses the recorded versions, and Restore opens them in tabs where they differ from yours. Modules are part of workspace backups and of GitHub Sync.

Indicators

Indicator methods on ctx return today's value. Each one is computed once over the whole history and then read bar by bar, so they are fast even inside parameter sweeps. Every indicator is causal: its value on a day only uses that day and earlier. Before enough history exists, they return NaN. Comparisons with NaN are always False, and you can check for it with isnan(x).

Every method accepts ago=k to read the value from k bars back. For example, a crossover happened today if ctx.sma(50) > ctx.sma(200) and ctx.sma(50, ago=1) <= ctx.sma(200, ago=1).

Vectorized Signals

Instead of on_bar, you can define signals(data). It receives the whole history at once (data.close, data.open, data.high, data.low, data.volume, data.dates, data.days as lists) and returns one target weight per bar, or None to hold.

def signals(data):
    fast = qt.sma(data.close, 50)
    slow = qt.sma(data.close, 200)
    return [1.0 if f > s else 0.0 for f, s in zip(fast, slow)]

The engine still applies weight i on bar i + 1. However, nothing stops signals from reading data.close[i + 1] by mistake. To catch that, QuantLab re-runs your function on histories cut off at several dates and compares the results. If any weight changes, the run is flagged Look-ahead detected, and its numbers are not achievable.

Portfolios

A strategy that defines UNIVERSE is a portfolio strategy. The Market panel then picks several instruments, starting from that list, and the backtest runs them together on one calendar: the union of their trading days. An instrument can't trade before its first bar or on a day it has no bar; it is valued at its last price in between. Indicators use each instrument's own bars.

UNIVERSE = ["SPY", "TLT", "GLD"]

def on_bar(ctx):
    if ctx.state.get("month") == ctx.day.month:
        return None                               # keep everything
    ctx.state["month"] = ctx.day.month
    up = [t for t in ctx.tickers if ctx[t].price > ctx[t].sma(200)]
    return {t: 1 / len(up) for t in up}             # tickers left out go to 0

ctx['SPY'] has everything a single-instrument ctx has: prices, every indicator, position, weight, is_long, entry_price, order(). The portfolio ctx adds ctx.tickers, ctx.weights, ctx.positions, ctx.gross and ctx.net. Return a dict of weights, a list in ticker order, or None. signals(data) works too: data['SPY'].close is a list on the shared calendar (NaN before the first bar), data.array('close') a NumPy matrix, and it returns {ticker: [weight per bar]} or one dict per bar.

Weights whose absolute values add up to more than the leverage limit are scaled down together. Sells execute before buys, and buys share the cash. The results show a Weights chart and an Attribution table: each instrument's P&L (trades, costs, dividends and borrow fees), which with interest on cash adds up exactly to the account's P&L. Without a benchmark the comparison is an equal-weight portfolio of the same instruments, rebalanced daily. In Python use engine.backtest_portfolio(strategy, [ds1, ds2, ...]).

Machine Learning

Strategies can import numpy, pandas, scipy and sklearn (scikit-learn). QuantLab loads what your code imports the first time you run it. NumPy (12 MB) ships with the site. pandas, SciPy and scikit-learn download from the Pyodide CDN on first use: scikit-learn needs SciPy, about 75 MB in all. The browser caches them afterwards.

PyTorch and TensorFlow don’t run in browsers: they have no WebAssembly build. There are three ways around that:

  • Write the network in NumPy. The Neural Network (NumPy) template is a two-layer network trained with Adam: the same forward pass, backward pass and optimizer step PyTorch runs for you.
  • Use scikit-learn’s models, including MLPClassifier / MLPRegressor neural networks, random forests and gradient boosting.
  • Run the engine in regular Python (see Running It Yourself). Strategy code is plain Python there, so import torch works like any other package.

Training Without Look-Ahead

The easy mistake in ML backtests is training on labels from the future. A label such as “the next day’s return” for bar i is only known at bar i + 1. walk_forward (available in every strategy) handles this. It retrains on a fixed schedule, gives each model only the rows whose labels were already known, and returns one out-of-sample prediction per bar:

import numpy as np
from sklearn.linear_model import LogisticRegression

def fit_predict(X_train, y_train, X_new):
    model = LogisticRegression().fit(X_train, y_train > 0)
    return model.predict_proba(X_new)[:, 1]          # probability the next day is up

def signals(data):
    c = data.close
    X = np.column_stack([qt.roc(c, 5), qt.roc(c, 20), qt.rsi(c, 14)])
    y = np.array([c[i + 1] / c[i] - 1 if i + 1 < len(c) else NAN for i in range(len(c))])
    prob = walk_forward(X, y, fit_predict, min_train=504, retrain_every=63, horizon=1)
    return [1.0 if p > 0.55 else 0.0 for p in prob]

Cross-Validating a Model

To measure how good a model is (not to trade it), use purged cross-validation. Ordinary k-fold leaks the future when labels span several days; purging drops training rows whose label window overlaps the test fold, and the embargo drops the rows just after it (López de Prado 2018).

res = cv_score(X, y, fit_predict, score=lambda y_true, y_pred: ..., k=5, horizon=5, embargo=5)
for train, test in purged_kfold(len(y), k=5, horizon=5, embargo=5): ...
for train, test, groups in cpcv_splits(len(y), n_groups=6, n_test=2, horizon=5): ...   # 15 splits, 5 paths

These functions train on data after the test fold as well, so their predictions must never be returned from signals: the look-ahead check would flag them.

Fit any scaling (means, standard deviations) inside fit_predict from the training rows, as the templates do. Scaling with statistics from the whole history leaks the future. Seed anything random (random_state=0, np.random.default_rng(0)) so results repeat; the look-ahead check also needs this. For slow models the look-ahead check samples fewer dates, marked (partial). Training happens on every run, so retrain monthly or quarterly rather than daily to keep runs fast.

Execution & Costs

Day t, at the closeon_bar sees prices up to day t and returns a weight or places orders.
Day t+1, at the openThe order fills at the open price (or at the close with Orders fill at: Next close), plus slippage and commission.
Day t+1, at the closeEquity is marked at the closing price. on_bar runs again.

Every fill records its arrival price, the close when the order was decided. The Implementation shortfall statistic averages how far fills landed from it, which captures the overnight delay as well as costs, the way trading desks measure execution.

This one-day delay is the most important rule in backtesting. Deciding and filling at the same price is a common backtest mistake, and it makes results look better than they could be in practice.

Sizing & Limits

Under Account & Execution → Sizing & Limits, rules resize the strategy's target weights at the close they are decided, using only prices up to that close, before the orders go out. They apply in this order, and every change they make is listed in the Constraint Log under the results:

  1. Target volatility multiplies the weights by target ÷ volatility, where volatility is that of the daily returns the proposed weights would have earned over the lookback (63 days by default), annualized. Fraction of Kelly multiplies them by fraction × mean ÷ variance of the same returns (never below 0). Neither goes beyond Max Leverage, and neither acts before a third of the lookback is available.
  2. De-risk at drawdown: once equity closes that far below its high, weights are multiplied by the de-risked size until the drawdown is back within half the trigger. The switch resizes the latest targets at once, even if the strategy issues no new ones.
  3. Max per instrument caps each |weight|; Max net scales the larger side so |longs − shorts| fits; Max gross scales everything so the sum of |weights| fits.

Share orders (ctx.order) and resting limit and stop orders aren't resized. The statistics Sizing & limit changes, Time de-risked and Avg. sizing scale summarize the log. In Python: engine.Config(sizing="vol_target", vol_target=0.1, dd_limit=0.15); the log is result.limits.

Significance Tests

The p-values are exact: the mean-return and alpha t-tests use Student's t, the win-rate test the binomial distribution. Daily returns are often autocorrelated (trend-following, smoothed or illiquid prices) and their volatility clusters, which makes ordinary t-statistics too large. The Newey-West t-statistics (for the mean return and for alpha) correct for both; when they are much smaller than the plain ones, believe them. The Lo-adjusted Sharpe annualizes the daily Sharpe ratio with the first ten autocorrelations rather than √252, and the effective sample size says how many independent days the returns are worth. The Probabilistic and Deflated Sharpe ratios allow for skew, fat tails and the number of versions tried. Monte Carlo Resampling adds block-bootstrap 95% confidence intervals for the Sharpe ratio, CAGR, volatility and maximum drawdown. All of these are in the Statistical tests group of the statistics picker.

How to Read Them Together

  • Sharpe is the usual headline, but it treats upside and downside swings the same. A Sortino much higher than Sharpe means most of the volatility is on the upside.
  • Max drawdown and longest drawdown are what it feels like to run the strategy with real money. A 50% drawdown needs a 100% gain to recover.
  • Beta below 1 with positive alpha means the strategy earned more than its market exposure explains. A low beta alone just means it held less of the asset.
  • Win rate means little alone. Trend followers often win 35% of trades and still profit because their average win is much larger than their average loss; check profit factor.
  • Fewer than about 30 trades or 3 years of data is too little to tell skill from luck. Run the Monte Carlo tool.
  • Every version you try counts. QuantLab counts the distinct versions of a strategy you have run on the same market (each change of code, parameters, settings or dates, plus every sweep and walk-forward candidate) and reports the Deflated Sharpe Ratio (Bailey & López de Prado 2014): the probability that the true Sharpe ratio beats the best you would expect from that many tries with no skill, using how much the tries' Sharpe ratios varied. The chip under the title shows the count; Reset Trials starts it again, for example when you begin a genuinely new idea.
  • The statistical tests answer “could this be luck?”. A p-value is the chance of a result at least this good if there were no real edge; below 0.05 is the usual bar. A minimum track record longer than your backtest means the data can’t yet show the Sharpe ratio is above zero. Test many variations and some will pass by chance, so treat one passing test as a hint, not proof.

Parameter Sweep

Choose one or two numeric entries from PARAMS and a list of values: 20:100:10 means 20, 30 … 100, and 5,10,20 lists values directly. Up to 400 runs. With Tune on: First 70%, each run is scored only on the first 70% of the period, and the last 30% is shown next to it as an out-of-sample check. Use these values in the editor writes the best combination into your PARAMS. Good parameters sit in a broad plateau of good results. A single bright cell is usually noise.

Every sweep ends with an overfitting check. Each run's daily returns are cut into 10 consecutive blocks; for every one of the 252 ways to call half of them in-sample, the setting with the best in-sample Sharpe is ranked against the others on the remaining half. The probability of backtest overfitting (PBO, Bailey, Borwein, López de Prado & Zhu 2015) is the share of splits where that winner ranks at or below the median. Above 50%, picking the best setting is worse than picking at random. The check also reports the winner's Sharpe ratio in and out of sample and the Sharpe hurdle: the best result expected from that many settings with no skill.

Walk-Forward Optimization

Choose parameters and values like a sweep, a training window and a test window. Starting after the first training window, the setting with the best score over the training window (or over everything so far, with Anchored) is used for the next test window; then both windows move forward by one test window. The stitched test windows are the out-of-sample result, compared with the setting that looks best in hindsight and with the benchmark. Walk-forward efficiency is the out-of-sample CAGR as a share of the CAGR the chosen settings showed while being tuned. Each candidate runs as one continuous backtest, so the switch between settings at a window boundary is assumed to cost nothing.

Monte Carlo Resampling

Takes the strategy’s daily returns and builds alternative histories by stitching together randomly chosen blocks of consecutive days (a circular block bootstrap). Blocks keep calm and volatile stretches together. The fan chart shows the range of paths, and the table shows percentiles of total return, CAGR and maximum drawdown. If the 5th percentile drawdown would be unbearable, size the strategy down.

In-Sample vs Out-of-Sample

Runs one continuous backtest and reports statistics separately before and after a split date. Indicator warm-up and open positions carry across the split. A strategy designed by looking at the whole chart will almost always look worse after the split, and that worse result is the realistic one.

Start/End Surfaces

A backtest's result depends on the dates you picked. This tool scores every window instead: for each start date s and end date e with s < e, S(s, e) is the chosen statistic of your strategy backtested from s to e (fresh starting cash on s, indicators warmed up on the history before it), and B(s, e) is the same statistic of the benchmark over that window (buy and hold, the benchmark you picked, or equal weight for a portfolio). Statistics: total return, CAGR, Sharpe, Sortino, volatility, max drawdown and Calmar, defined exactly as in the results table.

Start and end dates are the first trading day of each month, quarter or year in your date range, plus its last day. The two surfaces are drawn on one colour scale (clipped at the 2nd and 98th percentiles of all values, so one extreme window doesn't wash out the rest), as heatmaps with start dates down the side and end dates along the bottom, or as 3D surfaces you can turn by dragging (or Shift + arrow keys). Hovering, or the arrow keys, shows a window's dates and both values. Shortest Window hides windows shorter than you pick: CAGR and Sharpe ratios over a month or two swing wildly. The summary counts the windows where the strategy beat the benchmark (lower volatility, shallower drawdown), and Download CSV gives every window.

It needs one backtest per start date, not one per window: the engine only ever uses data up to each bar, so a backtest from s to e is the backtest from s to the last date cut at e, and each row comes from a single run. The tests check every statistic against performance() on each slice and cells against separate backtests of their windows.

Strategy Ranking

Backtests every built-in strategy (and, if you tick it, your saved ones) once with its default parameters on the instrument picked on the Backtest tab, with your benchmark, date range and settings, and ranks them by the statistic you choose (lowest first for volatility). Portfolio strategies run on their own UNIVERSE; the Market column says which. Strategies that short need Allow shorting, or they run long-only. Changing Rank By re-ranks the same runs without running them again. A strategy that fails is listed with its error and the rest still rank.

The best of many strategies tried on the same history looks better than it is, so the summary reports the winner's Deflated Sharpe, counting every strategy ranked as a trial and using the spread of their Sharpe ratios, and the probability of backtest overfitting (CSCV over 10 blocks) among the strategies on identical dates. Bars and the growth-of-100 chart show the field and the top five; Open loads a strategy on the Backtest tab and Download CSV saves the table. Engine: rank_strategies().

Every Instrument

Runs the strategy in the editor, with its default parameters, your date range and settings, on every loaded instrument (synthetic demo data skipped unless you untick it), and compares each run with buying and holding that same instrument; your benchmark setting is ignored here. The summary counts the instruments where the strategy did better on the statistic you pick (lower volatility, or a shallower drawdown, counts as better), with an exact one-sided sign test of "better on more than half" (ties left out) and a one-sided t-test of the average improvement. Instruments move together, so these aren't independent tests and the p-values are optimistic. The scatter plots each instrument's strategy value against its buy-and-hold value; points on the better side of the diagonal are green. Open shows the strategy on that instrument on the Backtest tab. Portfolio strategies (with a UNIVERSE) can't use this tool. Engine: strategy_breadth().

Risk Report

Runs the strategy once and analyses its daily returns and the holdings on its last day.

  • Factor regression. The strategy's daily return above the risk-free rate, regressed on the factors you list: a loaded ticker (its return above the risk-free rate, e.g. SPY), A-B for the return of A minus that of B (IWM-SPY: small minus large caps; TLT-SHY: duration), or a column of an uploaded factor file (ff3:SMB). Add Factor File reads daily factor returns such as the Fama-French files from Ken French's data library (unzip the CSV; YYYYMMDD dates and values in percent are recognized, and an RF column becomes the risk-free rate). Alpha is annualized (×252). Each estimate has an ordinary t-statistic and a Newey-West one (Bartlett kernel, ⌊4(n/100)2/9⌋ lags), which stays valid when residuals are autocorrelated or their volatility changes; p-values are two-sided from Student's t. Return attribution splits the mean excess return into alpha plus beta × each factor's mean return, which add up exactly. Variance decomposition gives each factor's share, beta × cov(factor, fitted return) / variance, plus the idiosyncratic rest; the factor shares add up to R².
  • Rolling beta and correlation to the benchmark over a window you choose.
  • Where the risk is. From the last 252 days of the instruments' returns, each final holding's volatility, marginal risk (∂σ/∂w), contribution (weight × marginal, adding up to the portfolio's volatility) and share of the risk, and the diversification ratio (weighted average volatility / portfolio volatility).
  • Stress tests. Ten well-known windows (the 2008 crisis, 2011 downgrade, 2015 devaluation, February 2018, Q4 2018, the COVID crash, the 2022 rate shock, March 2023 and August 2024) and one of your own. For each: what the strategy did if it was running, its drawdown within the window, and the final holdings replayed: each instrument's total return over the window × its final weight, which needs that instrument's data for the window. Benchmark shocks of −5%, −10% and −20% are applied through each holding's beta to the benchmark.
  • Value at Risk for the final holdings from a history you choose (500 days by default): historical (the holdings' P&L on each of those days), normal (from the covariance matrix) and Cornish-Fisher (normal adjusted for the P&L's skew and kurtosis), with expected shortfall and 10-day figures (historical from overlapping 10-day returns, normal scaled by √10). Component VaR splits the normal VaR by instrument. The Kupiec test checks the strategy's own history against a rolling 250-day historical VaR: a p-value below 0.05 with too many breaches means that VaR understated the risk.

Capacity

Re-runs the backtest at each account size you list with square-root market impact on (your impact coefficient, or 1 if it is off) and your participation limit, and reports CAGR, Sharpe ratio, drawdown, costs as a share of the starting cash, each fill's share of that day's volume (median and 95th percentile) and how many orders the limit spread over several days. Capacity is the size at which the Sharpe ratio falls to the share you pick of its value at the smallest size, interpolated on a log scale. It needs volume data, and it is an estimate: real impact depends on spreads, timing and other traders, so treat it as an order of magnitude.

Options Overlay (optional)

Adds options to a single-instrument strategy's long position: covered calls (sell calls a chosen percentage above the price), protective puts (buy puts below it) or a collar (both). Every N trading days, at the close, it opens options on the shares held then, expiring N days later; it pays the trading cost you set as a share of each premium, marks the options every day and settles them in cash at expiry against that close. Their P&L is added to the strategy's equity, and the statistics are shown with and without it.

This tool needs no option data: prices are modelled with Black-Scholes (European exercise, no dividends, the cash rate as the interest rate). The implied volatility is either the instrument's trailing realized volatility times a premium multiplier (implied usually runs above realized; 1.1 adds 10%) or the level of a loaded volatility index such as ^VIX that day, in percent, times the multiplier. There is no volatility skew, early assignment or bid-ask beyond the trading cost, so treat the result as a model of the trade-off (income against capped upside, insurance cost against smaller drawdowns), not as what fills would have been. To trade real quotes instead, import an option chain and use ctx.options (see Options).

Delta-hedged option. The same panel sells an at-the-money call on the starting cash's worth of the instrument every N days and hedges its delta with the instrument at every close. The hedged P&L is close to the sum of ½ × gamma × price² × (implied variance × Δt − the day's squared return): it earns when implied volatility was above the volatility that followed. It is split into the option's and the hedge's P&L, with that gamma-theta estimate alongside. Engine: bs(), implied_vol_series(), options_overlay(res, …) and delta_hedged(ds, …); tests check the prices against SciPy, put-call parity, finite-difference Greeks, an independent overlay ledger, and that a hedged option on simulated prices earns about nothing when implied equals the true volatility.

Sub-Period Consistency (optional)

Cuts one continuous backtest into 2–20 back-to-back periods with equal numbers of trading days and scores each against the benchmark. A strategy whose whole profit comes from one period depended on one market regime.

Cost Sensitivity (optional)

Re-runs the backtest once per cost level. Each level is the cost of every fill in basis points of traded value and replaces both the commission percentage and the slippage; the flat fee per fill is kept. The summary reports, by linear interpolation between the levels you tested, the cost at which CAGR drops below the benchmark’s and below zero.

Random-Timing Test (optional)

A permutation test of timing skill. It shuffles the strategy’s daily exposures, which keeps how often and how heavily it was invested but not when, and pairs them with the instrument’s actual close-to-close returns. Each ordering is scored by its Sharpe ratio before costs. The p-value is the share of shuffles that scored at least as well as the real ordering. Strategies that hold nearly the same position every day, like buy and hold, can’t be tested this way.

Speed & Caching

Sweeps and walk-forward grids run on several copies of Python at once: the main one plus helpers, up to four in all and one fewer than your processor cores, so one core is left for the page. Helpers start when you open the Research tab and stop after five idle minutes; results are identical to running one after another. Re-running a setup that hasn't changed at all (code, parameters, settings, dates, data and trial count) shows the earlier result straight away; it isn't added to the history again, and Re-run in the History tab always runs for real. When only settings change, a signals strategy reuses the signals it already computed for the same code, parameters and data, so costs and sizing can be explored without re-training a model; its print output is replayed. This assumes your code gives the same answer each time, so seed anything random. Any change to the data clears these caches.

Instrument Analytics

Buy-and-hold statistics for each loaded instrument, a correlation matrix of daily returns on the dates all of them share, and a growth-of-100 chart. Assets with low correlation combine into portfolios with smaller drawdowns.

Options

Strategies can trade listed options from real end-of-day option chains. QuantLab doesn't come with option data: historical chains are licensed, so you bring your own files and they stay in your browser. Common sources are CBOE DataShop (Option EOD Summary), OptionsDX, ORATS, OptionMetrics IvyDB (through WRDS), and data vendors such as Polygon, ThetaData or IVolatility, which can export CSV files.

Importing chains

Drop the files on the Data tab (CSV, TSV or TXT; unzip archives first). A file is read as an option chain when it has a quote date, an expiration and a strike column and either a call/put column with bid and ask, or call and put bid and ask columns side by side. QuantLab recognizes these layouts:

  • CBOE DataShop: underlying_symbol, quote_date, expiration, strike, option_type, bid_eod, ask_eod …. It uses the end-of-day bid and ask (the 15:45 ones when those are missing), the 15:45 implied volatility and delta, and active_underlying_price_1545.
  • OptionsDX: [QUOTE_DATE], [EXPIRE_DATE], [STRIKE], [C_BID], [C_ASK], [P_BID], [P_ASK], [C_IV], [C_DELTA] …, calls and puts on one row.
  • ORATS: tradeDate, expirDate, strike, callBidPrice, callAskPrice, putBidPrice, putAskPrice, callMidIv, putMidIv, delta, stockPrice …. The put's delta is the call's minus 1.
  • OptionMetrics: date, exdate, cp_flag, strike_price, best_bid, best_offer, impl_volatility, delta …. Its strike is in thousandths, so it is divided by 1,000; there is no underlying price, so load the stock's prices first for the strike filter.
  • Anything else with date, expiration, strike, type (C/P or call/put), bid, ask, plus optional last, volume, open_interest, iv, delta, underlying_price. Dates can be YYYY-MM-DD, MM/DD/YYYY or YYYYMMDD.

A full chain is large (a liquid ETF lists thousands of contracts a day), so the import keeps only what you'll trade: monthly (third-Friday) expiries, weeklies too, or all; contracts up to a number of days to expiry; strikes within a percentage of the spot; and an optional date range. The browser holds up to 4 million quotes per underlying. The files are read in pieces, so a file of several gigabytes works and can be cancelled. Files for the same underlying are merged (a contract and day that appears twice takes the later file's quote). The Option Chains table shows what is stored; Remove asks twice and can be undone. Chains aren't included in workspace backups; keep the original files. A test (tests/test_engine.py) runs the page's reader under Node and checks it reads every layout exactly as the engine's option_rows().

Trading options in a strategy

In on_bar(ctx), ctx.options is the chain of the instrument, as of today. In a portfolio strategy use ctx["SPY"].options. The underlying's prices must be loaded. Strategies using signals(data) can't trade options.

Fills, marks & expiry

  • An order placed on a bar fills on the next bar at that day's end-of-day quote: buys at the ask, sells at the bid. Options Fill At under Account & Execution can move the price halfway to the mid, or to the mid. A commission is charged per contract (default $0.65), and a contract is 100 shares (change Contract Multiplier for other contracts).
  • An order whose contract has no quote that day, a buy with no ask, or a sell with no bid doesn't fill. It is listed as unfilled and isn't retried, so the strategy decides again.
  • Open positions are marked at the mid every day. With no quote that day, the last mark is reused and counted as a stale mark.
  • On its expiry date, a contract settles in cash at its intrinsic value against the underlying's close. That gives the same profit as exercise or assignment followed by trading the shares at the close. An expiry on a market holiday settles at the close before it.
  • Not modelled: early exercise or assignment of American options, physical delivery into shares, the quoted size (any number of contracts fills at the quote), and margin. Short options are held against the account's cash with nothing set aside, so a run that sells options says so in its notes: check the collateral a broker would ask for.

A run that traded options gets an Options panel: option P&L, premium sold and bought, contracts and commissions, round trips and how many made money, expiries, unfilled orders, a chart of the positions' marked value and dollar delta, and every fill and settlement. Option Fills CSV exports them. The run's provenance records each chain's fingerprint. The templates in Options (Needs Option Data) sell covered calls, sell cash-secured puts with a profit target, and hold protective puts. The engine's tests check fills, marks and settlement against an independent ledger, and check that removing future quotes changes nothing before them.

Paper Trading & the Broker Bridge

Next Session. Every backtest also asks the strategy for its decision at the last close and shows the orders it would send for the next bar, sized at that close (inside the rebalance band: none), plus resting limit and stop orders. Download them as CSV or copy them as JSON. In Python: engine.backtest(..., decide_last=True).next.

Paper accounts (Paper tab) freeze the strategy code, modules, settings, market and a start date. Update with Latest Data re-runs the frozen setup from its start date on the data loaded now (add the newest prices on the Data tab first) and shows the account's equity, positions and next orders. Each update is logged with the code hash and data fingerprints, and if equity on a day recorded earlier comes out different (revised prices, a different engine), the account says so and keeps both. Nothing is sent anywhere.

Broker bridge (optional, needs a server). The page never talks to a broker. tools/bridge/broker_bridge.py is a small standard-library server you run yourself; Send to Bridge POSTs the next orders to it as JSON with a shared secret, after you confirm. It checks the secret, logs every request to bridge-log.jsonl, and by default only answers with the orders it would place (dry run). With --alpaca it places them in an Alpaca paper account (keys from APCA_API_KEY_ID and APCA_API_SECRET_KEY); --alpaca --live uses the live account. Orders filled at the next open become market-on-open orders (opg), at the close cls; fractional quantities go as day orders. Use it with care: a backtest is not a trading system, and nothing here checks your broker's positions before sending.

python tools/bridge/broker_bridge.py --secret my-secret              # dry run on localhost:8787
python tools/bridge/broker_bridge.py --secret my-secret --alpaca     # Alpaca paper account

Sharing, Reviews & Model Cards

Share links. In the History tab, a run's Details has Copy Share Link: a link to this page with the run's code, modules, settings, market, results, comments and model-card text compressed into the part after #, which browsers never send to the server. Whoever opens it sees what it is and can Load & Run It: the code is saved as a strategy, the settings and market applied, and the run checked against the shared numbers (it reproduces exactly when they have the same data; the price data itself isn't in the link).

Comments & model cards. Each run can carry a comment thread and a purpose and limitations text. Model Card turns them into a printable document (or Markdown) with what QuantLab knows about the run: market and period, execution and cost assumptions, financing, results, significance and the number of trials, data fingerprints and calendars, code hash, engine version, the run's notes, reviews and comments, and the code.

Audit log. Approve or Reject on a run (enter your name first) appends an entry to the audit log: time, run, a SHA-256 digest of the run's code, data, settings, market and results, the decision, the reviewer and a note. Pitfalls

  • Overfitting. With enough parameters, any rule fits the past. Prefer few parameters and round numbers, and always check out of sample.
  • Look-ahead bias. on_bar can’t see the future, but signals and ctx.custom can if you index past i. Watch for the look-ahead flag.
  • Survivorship bias. Testing on AAPL or NVDA today picks winners in hindsight. The stocks that failed over the last 10 years aren’t in your list.
  • Costs. A strategy trading daily pays slippage every day. Raise slippage to 5–10 bps and see whether the edge survives.
  • Regimes. Ten years of daily data includes only a few bear markets. A rule that “always worked” may have worked in just one kind of market.
  • Dividends. They aren’t in Nasdaq's prices; see Getting data.

Running It Yourself

QuantLab is a static website: HTML, JavaScript and a Python file, with no server-side code. The Python runtime (Pyodide 0.26.4) is included in pyodide/, so it also works without internet access.

# from the quantlab folder
python -m http.server 8000
# then open http://localhost:8000

Opening index.html directly from disk doesn’t work, because browsers block pages loaded that way from reading engine.py. To publish the site, push the folder to a GitHub repository and turn on GitHub Pages.

The engine also works as a normal Python module, with no dependencies of its own. Strategies may import anything installed, including PyTorch:

import engine
ds = engine.load_csv("SPY.csv", "SPY")
strat = engine.Strategy.from_code(open("my_strategy.py").read())
res = engine.backtest(strat, ds, engine.Config(cash=10_000, slippage_bps=5))
stats, bench = engine.summarize(res)
print(f"CAGR {stats['cagr']:.2%}  Sharpe {stats['sharpe']:.2f}  MaxDD {stats['max_drawdown']:.2%}")

Tests: python tests/test_engine.py, or python -m pytest tests.
